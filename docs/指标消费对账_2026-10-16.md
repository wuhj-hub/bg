# 指标消费对账报告（分支 B 定范围）

> 2026-10-16 ｜ 方法：静态扫描 bg 仓库全量 258 个 `.py` + 23 个 workflow，正则定位每个 `*_latest.json` 字面量的**生产者/消费者**，并按文件性质分类
> 目的：用证据判断「指标层抽象（分支 B）」值不值得做、做多大范围

---

## 一、结论摘要

- 共扫出 **50 个 `*_latest.json` 指标**。
- 其中 **18 个被 ≥4 个「语义消费者」**（读字段做业务判断）使用，**21 个被 ≥3 个**使用，**21 个是长尾（≤1 个消费者，不值得抽象）**。
- 消费者分三类，必须区分对待：
  - **语义消费者**（读字段判断）→ 这才是分支 B 的对象，共 18 个热点指标；
  - **审计消费者**（只查存在性/新鲜度：`artifact_audit`/`data_guard`/`pipeline_audit`/`run_and_verify`/`silent_failure_audit`…）→ 已由 `config/daily_artifacts.json` 覆盖，**不需要**字段抽象；
  - **副本消费者**（`skills_backup/盘前市场报告/scripts/*`）→ 影子副本，应先去留，而非抽象。

**判断**：分支 B 有价值，但**不该全量铺开（50→重构成 50 个 registry 条目）**。合理范围是「语义消费者 ≥4 的 ~18 个指标」，且形态应为**只读访问层**而非重写业务。

## 三、三类「口径分散」实证（分支 B 的真实靶点）

### 模式 1 · 同一数值字段，语义解释散落各处（`market_width.score`）
同一字段 `score` 被两类消费者赋予**不同语义修饰**：
- `env_engine`：把它视为「**含最高 +30 赚钱效应加成、天然偏高**」，用锚点下压 `[(40→35),(55→50)]` 后再入温度；这条知识**硬编码在 env 里**。
- `gen_premarket_report` / `gen_review_report`：直接展示 `score`+`level`（不下压）。
- 启示：字段一致，但「该怎么理解这个数」的判断散落在消费者代码里——正是「同一指标多个答案」的温床。

### 模式 2 · 文本型指标被多处正则解析（`quant_results_latest.json` 的 beast stdout）
`quant_results_latest.json` 实为各系统 **stdout 文本集**；`env_engine` 用
`re.search(r"安全评分[:：]\s*(\d+(?:\.\d+)?)\s*/\s*100", beast.stdout)` 提取「安全评分」，
其它脚本各自写正则/容错。同一语义被多份正则解析 → 改一处易漏另一处。

### 模式 3 · 并行副本脚本仍在读同一文件（`hot_emotion_latest.json` 有 **6 个**副本消费者）
`skills_backup/盘前市场报告/scripts/` 下的 `glm_brief` `data_guard` `sync_hot_emotion` `hot_emotion` `market_chain` `push_hot_emotion` 与主脚本重复，读同一 latest。
→ 分支 B 之前应**先决定影子副本去留**，否则抽象会被副本稀释。

### 洞察 4 · 「生产者」本身就是隐式契约
多数 latest 由变量名拼路径写出，静态无法从字面量定位生产者。说明**「指标 → 生产者 → schema → 消费者」这条契约目前是隐式的**——这恰好是 registry 最该固化的东西。

## 四、分支 B 建议范围与形态

**范围（建议）**
1. **优先**：语义消费者 **≥4 的 18 个指标**（覆盖绝大多数业务判断路径）；第一阶段只做 **top 8**：`market_width` `quant_results` `rsv_strength` `信号仲裁` `qiankun_a` `yearline_breadth` `四维共振` `板块共振`。
2. **不动**：21 个长尾指标（≤1 消费者）、审计类消费者（已有 `daily_artifacts.json`）。
3. **前置**：副本脚本（skills_backup）去留决策。

**形态（低风险）**
- 建**只读访问层** `metrics.py`（`report_io` 的姊妹）：`load(name)->dict` + 字段级 accessor（如 `safety_score()`、`width_score()`），**把「字段定义+语义修饰」收口到一处**。
- **不强制改造全部消费者**：新代码/改动代码走新层；存量按热点**渐进**迁移，每个指标改动做**影子对拍**（本体系历史教训：改脚本易引回归）。
- 顺带产出显式 **指标注册表**（名 → 生产者 → schema → 消费者），补上「契约」这一环。

## 五、边界与风险

- 本对账为**静态**结果：生产者/schema 部分依赖字面量，存在漏识别（表中 `?`）；字段级使用为抽样人工核验。
- 收益主要在**未来维护**，非当前正确性——没有已知故障由「指标口径分散」直接引起（真问题已由取数层 / 副本层治理解决）。
- 因此**建议先做 top-8 试点、验证收益**，再决定是否扩到 18 个；不主张一次性大重构。
